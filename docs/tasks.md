    - Избегать дублирования сообщений (проверки senderId)

12. 🗄️ **DATABASE BEST PRACTICES:** При работе с TypeORM:

**Архитектурное решение - Event Emitter:**
```typescript
// Решение проблемы circular dependency между CallService и CallGateway
@Injectable()
export class CallService {
  constructor(
    @InjectRepository(Call)
    private callRepository: Repository<Call>,
    private eventEmitter: EventEmitter2, // Event Emitter вместо прямого вызова Gateway
  ) {}

  // Emit события вместо прямых вызовов
  async createCall(initiateCallDto: InitiateCallDto, callerId: string): Promise<Call> {
    const call = await this.callRepository.save({...});
    
    // Emit событие для Gateway
    this.eventEmitter.emit('call.created', { call, callerId, receiverId });
    
    // Автоматический переход в статус RINGING
    await this.updateCallStatus(call.id, CallStatus.RINGING);
    
    return call;
  }
}
```

```typescript
// WsJwtAuthGuard для проверки JWT в WebSocket соединениях
@Injectable()
export class WsJwtAuthGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const client = context.switchToWs().getClient();
    const token = client.handshake.auth.token;
    
    try {
      const payload = this.jwtService.verify(token);
      client.data.user = { id: payload.sub, username: payload.username };
      return true;
    } catch {
      return false;
    }
  }
}
```

```
User1 (телефон 1) → User2 (телефон 2)
```

5. **WebRTC конфигурация:** Неправильные настройки в Flutter WebRTC

**Диагностика:**
- [ ] **Проверить логи WebRTC** на обоих устройствах
- [ ] **Проверить ICE candidates** в CallSocketClient
- [ ] **Проверить медиа потоки** в WebRTCService

**Статус:** 🚨 **КРИТИЧЕСКАЯ ПРОБЛЕМА** (25.08.2025)

- ❌ **При перезаходе** всё работает нормально
- 🔍 **Причина:** Отсутствует автоматическое обновление JWT токенов

**Текущее состояние:**
```
JWT токен: expires in 24 hours
├── ✅ Первые часы: всё работает нормально

└── ✅ При повторной авторизации: всё восстанавливается
```

**Возможные причины:**
1. **Refresh token не используется** для автоматического обновления
2. **Frontend не проверяет** срок действия токена
3. **Backend не отправляет** refresh token при login
4. **AuthService не обрабатывает** 401 ошибки автоматически

**Решение:**
- [ ] **Backend:** Добавить refresh token в login response
- [ ] **Frontend:** Автоматическое обновление токена при 401
- [ ] **AuthService:** Обработка expired токенов
- [ ] **Тестирование:** Проверка работы refresh токенов

  - **Проблема:** После завершения звонка экран `ActiveCallScreen` закрывался некорректно, что иногда приводило к появлению пустого зеленого экрана.

  - **Проблема:** Звук стабильно шел только в одну сторону. Логи бэкенда показывали предупреждения `callId: null` при получении ICE-кандидатов.
  - **Решение:** В `webrtc_service.dart` реализована буферизация исходящих ICE-кандидатов. Теперь кандидаты накапливаются и отправляются на сервер только после получения `callId` от бэкенда через событие `call_initiated`. Это устранило гонку состояний и сделало обмен сетевой информацией надежным.

- [x] **Диагностирована и устранена проблема с внешним аудиоустройством**
  - **Проблема:** Несмотря на исправления в коде, односторонняя слышимость сохранялась.
  - **Решение:** Пользователем было обнаружено, что на одном из тестовых устройств были подключены Bluetooth-наушники, которые перехватывали аудиопоток. Проблема была решена после их отключения.

- [x] **Произведена очистка кода**
  - **Описание:** Из файла `webrtc_service.dart` были удалены многочисленные отладочные `debugPrint`, добавленные в ходе диагностики. Основные исправления, повышающие стабильность, были сохранены.

- [x] **Решена проблема односторонней слышимости в браузере (Flutter Web)**
  - **Проблема:** При звонке с мобильного приложения на веб-версию, звук от телефона не воспроизводился в браузере из-за строгой политики автовоспроизведения (Autoplay Policy).
  - **Решение:** В `active_call_screen.dart` для веб-платформы был добавлен невидимый HTML-элемент `<audio>`. Удаленный медиапоток принудительно привязывается к этому элементу и запускается через `play()`, что является надежным способом обойти ограничения браузера и обеспечить воспроизведение звука.

- [x] **Исправлены критические ошибки в веб-версии**
